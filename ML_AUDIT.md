# ML Strategy — Bug Audit

> Generated by systematic code review of `backend/strategies/ml_strategy.py`, `backend/ml/train.py`, `backend/ml/features.py`, `backend/ml/stacking.py`, `backend/ml/model.py`, `backend/api/ml_routes.py`.

---

## Critical Bugs

### C1. Online learning target misalignment with `forecast_horizon > 1`
**File:** `backend/strategies/ml_strategy.py:159-160`

```python
actual_target = int(data.iloc[i]["close"] > data.iloc[i - 1]["close"])
```

The online learning update always computes a 1-bar forward return (`close[i] > close[i-1]`), but the model may have been trained with `--forecast-horizon N` where N > 1. In that case, the model predicts `close[i+N] > close[i]`, but the partial_fit updates it with the wrong target function.

**Fix:** Store `forecast_horizon` from metadata and compute `actual_target = int(data.iloc[i]["close"] > data.iloc[i - forecast_horizon]["close"])` when `i >= forecast_horizon`.

---

### C2. `list_models()` returns entries with wrong names from latest-metadata files
**File:** `backend/ml/model.py:136-177`

The glob `*_metadata.joblib` matches **both** the versioned files (`foo_v1_metadata.joblib`) **and** the latest-symlink files (`foo_metadata.joblib`). The filename parser in lines 141-150 extracts the wrong `name` from the latest file — it strips `_metadata` but leaves a trailing underscore (e.g. name becomes `"multi_symbol_model_"` instead of `"multi_symbol_model"`). This creates duplicate entries with slightly different names, or worse, causes the API to return models with mangled names.

**Fix:** Explicitly skip files whose stem doesn't contain `_v`, or specifically exclude `{name}_metadata.joblib` without `_v{version}`.

---

### C3. `_apply_metadata_params` can't distinguish "user explicitly set to default" from "not set"
**File:** `backend/strategies/ml_strategy.py:119-141`

```python
if self._user_params["max_hold_bars"] == 30:
    mhb = train_params.get("max_hold_bars")
    if mhb is not None:
        self.max_hold_bars = int(mhb)
```

If a user explicitly passes `max_hold_bars=30` (which is the default), the metadata value is **silently** ignored. Same for `confidence_threshold=0.55`, `trailing_stop_pct=0.05`, and `use_kelly=False`.

**Fix:** Use a sentinel object (e.g. `_UNSET = object()`) for each param, not the default value.

---

### C4. Subprocess pipe deadlock in retrain API
**File:** `backend/api/ml_routes.py:79-84`

```python
proc = subprocess.Popen(
    cmd,
    stdout=subprocess.PIPE,
    stderr=subprocess.STDOUT,
)
```

`PIPE` is never read — if training produces enough output, the OS pipe buffer fills up and the subprocess **blocks forever** (deadlock).

**Fix:** Redirect to a log file instead (`open("path/to/log", "w")` as `stdout`), or use `subprocess.DEVNULL`, or spawn a reader thread.

---

### C5. Grid search doesn't tune SGD or MLP parameters
**File:** `backend/ml/train.py:976-993`

`_grid_params()` only generates hyperparameter combinations for tree-based models (`rf`, `gbt`, `xgb`, `lgb`). For `sgd` and `mlp`, it still passes `n_estimators` and `max_depth` which are meaningless for those model types. No SGD-specific params (penalty, alpha, learning_rate) or MLP-specific params (hidden_layer_sizes, alpha_mlp, learning_rate_init) are ever grid-searched.

**Fix:** Add dedicated param grids for `sgd` and `mlp` model types.

## High-Priority Bugs

### H1. `_position_size` returns Kelly fraction as cash *amount*, but uses `prob_up` before it's validated
**File:** `backend/strategies/ml_strategy.py:62-72`

When `use_kelly=True`, the size is `portfolio.cash * fraction` without checking if the prediction is actually above threshold. This means even a low-confidence prediction (e.g., prob_up=0.51) could trigger a buy with Kelly sizing, bypassing the confidence threshold check that comes later in `next()`.

Actually the flow protects this: `next()` only calls `_position_size` inside the `if prob_up >= self.confidence_threshold` block (line 200-201). So this is **not a bug** — the call site guards it. But it's worth documenting since `_position_size` doesn't enforce the threshold itself.

---

### H2. Trailing stop `_peak_price` initialized to 0.0, causing silent skip on first bar
**File:** `backend/strategies/ml_strategy.py:48, 187`

```python
self._peak_price = 0.0
...
self._peak_price = max(self._peak_price, price)
```

On the very first bar where `has_position` is True, `max(0.0, price)` sets `_peak_price = price`. But the trailing stop check at line 195 requires `self._peak_price > 0` — this is fine since the first bar sets it. However, if position was entered externally (without the strategy setting `_entry_bar`/`_peak_price`), the trailing stop won't work until `_peak_price` gets updated on a subsequent bar.

**Impact:** Minor — the first bar's price is always the peak, so trailing stop on that one bar is effectively 0%, which could trigger an immediate exit if checked.

---

### H3. `has_position` dual-tracking can desync
**File:** `backend/strategies/ml_strategy.py:182, 205, 231`

```python
has_position = self._has_position or portfolio.positions.get(symbol, 0) > 0
...
self._has_position = True   # line 205 (on BUY signal)
...
self._has_position = False  # line 231 (_exit_position)
```

If the backtest engine externally closes the position (e.g., end of simulation), `self._has_position` stays `True` while `portfolio.positions` is 0. The next bar's `has_position = True or 0 > 0 = True`, so exit logic still runs. But by then `_peak_price` might be stale.

---

### H4. Context data download may fail silently with wrong timestamp types
**File:** `backend/strategies/ml_strategy.py:96-112`

```python
start_date = data.index.min()
end_date = data.index.max()
...
ctx_df = ticker.history(start=start_date, end=end_date, auto_adjust=True)
```

`data.index` is a DatetimeIndex (possibly timezone-aware). yfinance's `start`/`end` expects date-like values, but timezone-aware Timestamps might not be handled correctly by the Yahoo API. Also, the `end` parameter is often exclusive in yfinance (stops before midnight), which could miss the last day's data.

---

### H5. `_calc_metrics` crashes on empty returns series
**File:** `backend/ml/train.py:514-517`

```python
returns = pd.Series(snapshots).pct_change().dropna()
sharpe = round(
    (returns.mean() / returns.std() * np.sqrt(252))
    if returns.std() > 0 else 0, 2)
```

If there are fewer than 2 snapshots, `pct_change()` produces all NaNs, `dropna()` gives an empty Series. `returns.mean()` returns NaN, `returns.std()` returns NaN. The `if returns.std() > 0` check returns `False` (NaN > 0 is False), so it falls through to `0`. But `returns.mean()` would be used for other metrics — no crash, but silently returns 0 which could be misleading.

---

### H6. `merge_context_features` joins on index — fragile with timezone mismatches
**File:** `backend/ml/features.py:219-221`

```python
df = df.join(ctx_feat, how="left")
for col in ctx_feat.columns:
    df[col] = df[col].ffill()
```

`df.join` matches on the index. If the main DataFrame's index is timezone-aware but the context DataFrame's index is timezone-naive (or vice versa), the join will produce all-NaN columns. The `ffill()` then carries nothing forward. This would silently produce zero-information context features.

---

### H7. Division by zero in feature computation (multiple locations)
**File:** `backend/ml/features.py`

Several divisions aren't guarded:

| Line | Expression | Risk |
|------|-----------|------|
| 58 | `close / data["sma_20"]` | sma_20 could be 0 (first 20 bars) |
| 62 | `volume / data["vol_ma_20"]` | vol_ma_20 could be 0 |
| 70 | `avg_gain / avg_loss` | avg_loss could be 0 |
| 93 | `(highest_20 - lowest_20)` replaced with NaN | guarded |
| 118 | `(bb_upper - bb_lower) / bb_mid` | bb_mid could be 0 |
| 161 | `pos_mf / neg_mf` | neg_mf could be 0 |
| 187 | `atr_sum / h_l_range` inside `log10` | both could be 0 |

Some are guarded with `.replace(0, np.nan)` but others aren't, leading to `inf` values in the feature matrix.

## Medium-Priority Bugs

### M1. Multi-horizon models leak into stacking ensemble
**File:** `backend/ml/train.py:803-806`

```python
base_models: dict[str, object] = {}
for label, model, _ in results:
    key = label.split()[-1].lower()
    base_models[key] = model
```

If `--multi-horizon` is enabled, `results` includes multi-horizon models (label like `MH-RF(1,5,21)`). The stacking ensemble will try to use `MultiHorizonEnsemble` objects as base learners. A stack of stacks is probably not intended.

---

### M2. `StackedEnsemble` doesn't clone the meta-model before fitting
**File:** `backend/ml/stacking.py:100`

`self.meta_model.fit(meta_features, y)` mutates the meta-model in-place. If the ensemble is refit, the meta-model's state carries over. `LogisticRegression` has `warm_start=False` by default, so `fit()` resets coefficients. But this is fragile.

---

### M3. `MultiHorizonEnsemble.fit()` uses same hyperparams for all horizons
**File:** `backend/ml/stacking.py:253`

```python
model = train_model(clean, feature_cols, self.base_model_type, **self.base_params)
```

A 1-day horizon model might need very different hyperparameters (e.g., more trees, shorter lookback) compared to a 21-day model. Using the same params for all horizons is suboptimal.

---

### M4. Walk-forward purge logic may drop too many rows
**File:** `backend/ml/train.py:280-286`

```python
unique_ts = train_df.index.unique().sort_values()
pos = int(unique_ts.searchsorted(val_min_ts, side="left"))
if pos > 0:
    cutoff_ts = unique_ts[max(0, pos - purge_window)]
    train_df = train_df[train_df.index < cutoff_ts]
```

`purge_window` = `forecast_horizon` in the call at line 1266. But `searchsorted` on unique timestamps may drop a different number of *actual rows* than intended, because each timestamp may have multiple rows (one per symbol). The subsequent `train_df = train_df[train_df.index < cutoff_ts]` removes **all** rows at or after `cutoff_ts` for **all symbols**, which is overly aggressive. The embargo at line 290 (`train_df.iloc[:-embargo]`) also operates on the multi-symbol DataFrame, potentially dropping data from symbols that had fewer recent bars.

---

### M5. `backtest_baseline` handles `initial_cash` per-symbol inconsistently
**File:** `backend/ml/train.py:440`

```python
cash_per_sym = initial_cash / n_syms
```

Each symbol gets an independent `Portfolio(cash_per_sym)`. But the ML model backtest (`backtest_model`) uses one shared portfolio across symbols. This makes the baseline comparison unfair — a multi-symbol ML model can allocate capital across symbols optimally, while the baseline divides cash equally and keeps it separate.

---

### M6. `tune_confidence_threshold` evaluates thresholds on validation set already used for model selection
**File:** `backend/ml/train.py:542-570`

When `--auto-threshold` is used with `--grid-search`, the threshold is tuned on `val_df`, which was already used to pick the best model/hyperparameters. This double-dipping on the validation set inflates performance estimates (optimization bias).

---

### M7. Out-of-fold predictions in `StackedEnsemble` use non-purged expanding windows
**File:** `backend/ml/stacking.py:70-103`

The `TimeSeriesOOF.split()` creates folds without any purge or embargo buffer between train and validation. For financial time series with autocorrelation, this leaks information across the fold boundary.

---

### M8. `RegimeAwareModel` column access is fragile
**File:** `backend/ml/stacking.py:315-322`

```python
if isinstance(X, pd.DataFrame):
    hurst = X.get("hurst", pd.Series([0.5] * len(X)))
    choppiness = X.get("choppiness", pd.Series([0.0] * len(X)))
```

If the DataFrame has columns `hurst` and `choppiness` but they're all-NaN (e.g., from the first 50 bars where Hurst can't be computed), the regime modulation still runs but on NaN values. `NaN > 60` is `False`, and `NaN < 0.45` is `False`, so no modulation happens — which is the desired safe behavior. But it's relying on a side effect of NaN comparison rules.

---

### M9. Multi-symbol feature alignment in `prepare_features`
**File:** `backend/ml/train.py:128-153`

```python
all_dfs: list[pd.DataFrame] = []
for sym, df in data_dict.items():
    d = compute_features(df.copy())
    d["symbol"] = sym
    ...
    all_dfs.append(d)
combined = pd.concat(all_dfs)
```

Different symbols have different date ranges. `pd.concat` stacks them. When `combined` is sorted by index at line 153 (`combined.sort_index(kind="mergesort")`), rows from different symbols are interleaved by date. This is correct for multi-symbol training, but the `backtest_model()` function assumes each symbol has contiguous blocks — it does `df[df["symbol"] == sym].sort_index()` which is fine since it re-extracts per-symbol.

---

### M10. `backtest_model` doesn't set `_symbol` on strategy objects
**File:** `backend/ml/train.py:298-427`

The `backtest_model` function calls `model.predict_proba(feat_df)` directly, not `strategy.next()`. So this is not actually a strategy-based backtest — it's a direct model evaluation. This is fine for evaluation, but the `MLStrategy` class's online learning and context-merging logic is never exercised during training backtests.

## Low-Priority Bugs / Cleanup

### L1. Walk-forward retrain on full data uses single model type
**File:** `backend/ml/train.py:1356`

```python
last_model = train_model(full_df, feature_cols, final_model_type, **params)
```

After walk-forward validation, the final model is retrained on **all** data using only the model type from the last fold's best model. This ignores stacking, multi-horizon, and regime-aware wrappers.

---

### L2. `_active_pids` in-memory state lost on server restart
**File:** `backend/api/ml_routes.py:16`

```python
_active_pids: dict[str, int] = {}
```

If the uvicorn server restarts, all tracking PIDs are lost. Orphaned subprocesses continue running but the API reports "unknown" for any status check.

---

### L3. `os.kill(pid, 0)` behavior differs on Windows
**File:** `backend/api/ml_routes.py:105`

On Windows, `os.kill(pid, 0)` raises `PermissionError` (a subclass of `OSError`) for processes owned by another user, but for non-existent processes it actually raises `ProcessLookupError` (also `OSError`). The blanket `except OSError` handles both, so functionally it works, but it's worth noting.

---

### L4. `_build_cmd` omits several CLI flags
**File:** `backend/api/ml_routes.py:19-53`

The following CLI flags are not exposed via the retrain API:
- `--embargo`, `--cutoff-date`, `--val-split`, `--triple-barrier-pct`, `--triple-barrier-max-bars`, `--regularize`, `--prune`, `--n-estimators`, `--max-depth`, `--learning-rate`, `--confidence-threshold`, `--base-buy-size`, `--model-dir`

Users relying on the API for retraining can't control these parameters.

---

### L5. Empty Sharpe calc edge case
**File:** `backend/ml/train.py:514-517`

Already documented in H5. When there are 0 or 1 trades, Sharpe = 0 is returned with no warning.

---

### L6. `backtest_baseline` hardcodes strategy params
**File:** `backend/ml/train.py:877-887`

```python
sma = backtest_baseline(
    val_df, SmaCrossover,
    {"short_window": 10, "long_window": 50},
    buy_size=1000,

```

These default parameters may not be optimal for the given symbols/time period, making the baseline comparison potentially unfair.

### L7. `train_model` silently accepts irrelevant kwargs
**File:** `backend/ml/train.py:626-712`

When `train_model("sgd", n_estimators=200, max_depth=10)` is called, the kwargs are ignored by the `SGDClassifier` constructor. No warning is printed. This is minor but makes debugging harder.

### L8. `save_model` tmp-replace race condition on Windows
**File:** `backend/ml/model.py:80-85`

```python
tmp.replace(latest_model)
```

If two processes save the same model simultaneously, the tmp file might be locked. Windows file locking is stricter than Unix.

---

### L9. `delete_model` version=None removes ALL files including latest links
**File:** `backend/ml/model.py:210-211`

```python
files = list(models_dir.glob(f"{name}*.joblib"))
```

This deletes `foo.joblib` (latest), `foo_metadata.joblib`, `foo_v1.joblib`, `foo_v1_metadata.joblib`, etc. — everything matching `foo*.joblib`. This is the intended behavior for `version=None`, but it could surprise users who expect only versioned files to be removed.

---

### L10. `MLStrategy.init()` re-fetches context data on every initialization
**File:** `backend/strategies/ml_strategy.py:94-114`

Every time the strategy is initialized (e.g., for each new backtest run), it downloads context data from yfinance. This is slow and could hit rate limits. Context data could be cached or passed as a parameter.

---

### L11. `MLStrategy.init()` context download silently catches all exceptions
**File:** `backend/strategies/ml_strategy.py:111-112`

```python
except Exception:
    pass
```

If context data download fails for any reason (network, API error, invalid symbol), it's silently ignored. No warning is printed, so the user doesn't know context features are missing.

---

### L12. Online learning update logged but not rate-limited
**File:** `backend/strategies/ml_strategy.py:154-165`

Every bar with `online_learning=True` triggers a `partial_fit` call. On high-frequency data (e.g., 1-min bars), this could be thousands of updates per session, potentially causing concept drift or overfitting to recent noise.
